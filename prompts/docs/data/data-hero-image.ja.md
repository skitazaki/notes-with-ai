# 画像生成プロンプト — データ ヒーロー画像

ドキュメント品質の概念ヒーローイラストを作成してください。

タイトルは「戦略的資産としてのデータ」。
サブタイトルは「価値創出と信頼性、統制、運用整合性を両立させる 4 つのレイヤー。」

この画像は、データ セクション全体の高レベルな概念モデルを導入するためのものです。
単にデータを収集して保存するだけではなく、4 つのレイヤーを 1 つの運用モデルとして接続することで、データが戦略的資産になることを表現してください。

- データ取得層（Source Layer）
- 活用基盤層（Enablement Layer）
- 価値創出層（Value Layer）
- 統制層（Control Layer）

特に、価値創出はエンジニアリングやアーキテクチャの基盤に依存していること、そしてガバナンス、セキュリティ、プライバシーは後付けではなく全体に組み込まれていることが伝わるようにしてください。

スタイル:

- クリーンな編集デザイン調インフォグラフィック
- 技術ドキュメント向けの現代的なベクター図解
- 明るい背景
- 5〜6 色程度の落ち着いたプロフェッショナルな配色
- 記事幅でも読めるラベル
- 16:9
- docs セクションのヒーロー画像として使える見た目
- 製品マーケティングではなく概念説明が主目的
- ベンダー中立
- ロゴや製品固有のブランド表現は使わない

構図:

上段に境界が明確なデータ取得層、活用基盤層、価値創出層を配置し、その 3 領域すべての下に連続した統制層を置いてください。活用基盤層には管理対象のデータフローと、それを支えるケイパビリティの両方が含まれるため、データ取得層や価値創出層より横幅を広くしてください。

上段の 3 領域そのものを同等の工程として描かないでください。これらは責任領域です。方向を持つ矢印は、領域の内外に設ける専用のデータフローだけに使ってください。

次のレイアウト階層を厳守してください。

1. **データ取得層:** 業務システム、デバイス、API、外部フィードが **データ収集** に集まる様子を描く。データ取得層内で名前を付けるライフサイクル上の活動はデータ収集だけにする
2. **プラットフォーム境界:** データ取得層と活用基盤層の間に明確な縦の境界を描く
3. **活用基盤層 — データフロー:** **データ取り込み** をプラットフォーム境界の直後、活用基盤層の内側に完全に収める。その後を **データ取り込み → Raw → Transform → Curate → Trusted** という明示的なフローにする。左から右への処理順序を構成する箱はこれらだけにする
4. **活用基盤層 — 横断ケイパビリティ:** **データエンジニアリング**、**データアーキテクチャ**、**データマネジメント**、**メタデータ** は、活用基盤層のデータフロー全体を横断して支える、順序を持たない帯、レール、または周囲のケイパビリティブロックとして配置する。各ケイパビリティを Ingestion、Raw、Transform、Curate、Trusted のいずれかに 1 対 1 で対応させない。ケイパビリティのラベル同士を矢印で結ばない
5. **価値創出層:** Trusted の先に分析、インサイト、AI / ML 活用、データ共有を配置する。これらは価値利用であり、活用基盤層の追加処理状態として描かない
6. **統制層:** ガバナンス、セキュリティ、プライバシー、コンプライアンス、ポリシー適用を、データ取得層、活用基盤層、価値創出層の下に続く一つの基盤として配置し、全体へ控えめな上向きの接続を入れる

各レイヤーには次の要素を反映してください。

データ取得層（Source Layer）:

- 外部フィード
- 業務システム
- デバイス
- API
- ソース側で行うデータ収集
- データ取り込みはこの領域に置かない

活用基盤層（Enablement Layer）:

- データエンジニアリング
- プラットフォーム基盤
- アーキテクチャ
- メタデータ
- データ品質
- データ取り込み
- Raw、Transform、Curate、Trusted のデータフロー

価値創出層（Value Layer）:

- 分析
- インサイト生成
- ダッシュボード
- AI / ML 活用
- データ共有

統制層（Control Layer）:

- ガバナンス
- セキュリティ
- プライバシー
- コンプライアンス
- ポリシー適用

データ取得層、活用基盤層、価値創出層は、接続された責任領域として描き、処理矢印は専用のデータフロー内だけに置いてください。
統制層は独立した 4 本目の列ではなく、3 つのレイヤー全体の下にある恒常的な信頼・統制の基盤として扱い、それぞれの段階へ上向きにつながる視覚表現を入れてください。

矢印、フロー、控えめな動線などを用いて、データが収集からプラットフォーム境界を越えて取り込まれ、Raw、Transform、Curate、Trusted を経て価値利用へ進むことを示してください。
また、オーバーレイ、境界線、接続線、連続した帯などを用いて、統制層が下にありながらもライフサイクル全体に効いていることを示してください。

小さく含める視覚要素:

- プラットフォーム境界より前にある、複数のソース種別からのデータ収集
- 活用基盤層の内側で、プラットフォーム境界を越えたデータを受け入れるデータ取り込み
- Raw → Transform → Curate → Trusted という明確なデータフロー
- エンジニアリング、アーキテクチャ、マネジメント、メタデータが工程に見えず、フロー全体を横断して支える構造
- メタデータと発見性
- 分析や共有の成果
- ガバナンスとセキュリティのガードレール

中心メッセージ:

データは、収集、確実な取り込み、基盤化、価値創出、統制を 1 つの一貫した運用モデルとして整合させたときに、戦略的資産になる。

小さなキャプション:

「データ価値は活用基盤の能力を介して創出され、信頼は継続的な統制によって支えられる。」

やってほしいこと:

- 4 つのレイヤーが 1 つの統合モデルとしてすぐ理解できるようにする
- データ収集をデータ取得層、データ取り込みを活用基盤層の内側に置き、両者を明確なプラットフォーム境界で分ける
- Raw → Transform → Curate → Trusted の順序を持つフローと、その全体を支える順序を持たない活用基盤ケイパビリティを明確に区別する
- データ取得層、活用基盤層、価値創出層の左から右への依存関係を明確にする
- 価値は強い活用基盤層に依存していることを強調する
- 統制層が下に描かれていても、全体に横断的かつ継続的に効いていることを示す
- ビジネス価値と運用上の厳密さのバランスを保つ
- 具体的な製品 UI ではなく、抽象的だがデータシステムらしいモチーフを使う

やってはいけないこと:

- 小さな要素が多すぎる密なアーキテクチャ図にしない
- データ取り込みをデータ取得層に置かない、データ収集とデータ取り込みを一つにまとめない、ランディングゾーンをソースや収集手段として描かない
- データエンジニアリング、データアーキテクチャ、データマネジメント、メタデータを連続工程として並べない、Raw、Transform、Curate、Trusted と 1 対 1 で対応させない、ケイパビリティのラベル同士を処理矢印で結ばない
- 統制層を後付けの機能、分断された別機能、または最後の下流工程として描かない
- データ領域が分析だけで成り立つかのように見せない
- 長いラベルや過剰なテキストを詰め込まない
- ベンダーロゴ、クラウドのブランド記号、ありがちなストックビジネス風素材を使わない
