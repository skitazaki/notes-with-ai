データメッシュは、多数のドメインにまたがるデータの所有と提供を拡張するためのデータアーキテクチャのパターンです。データを単なる副産物ではなくプロダクトとして扱い、意味や業務コンテキストを知っているドメインに責任を近づけつつ、共有基盤とガバナンス標準を使って全体の一貫性を保つことを重視します。

この考え方の本質は、データを分散すること自体ではなく、分散した状態で発見性、相互運用性、信頼性、説明責任を維持する方法を設計することにあります。データメッシュは、個々のドメインの自律性を高めながら、組織全体としての整合性を失わないための設計原則です。

本ページは、データメッシュを構成する4つの原則をアーキテクチャの観点から再整理した要約です。よりメタデータ中心の説明は [データメッシュとメタデータ](/ja/docs/data/metadata/data-mesh/) を参照してください。

## なぜデータメッシュが登場したのか

伝統的な中央集権型アーキテクチャは、少数のチームで管理されるデータ環境ではうまく機能します。集中型のデータウェアハウスや処理基盤は、共通定義や統制の強さを提供し、データの整合性を維持しやすいという利点があります。しかし、組織が大きくなると、中央のチームがデータ提供と意思決定の両方でボトルネックになりやすくなります。

問題は技術的な容量だけではありません。組織のスケールに対する協調の問題です。中央のプラットフォームはデータ処理を担えますが、営業、カスタマーサポート、物流、財務など多様なドメインが持つ業務コンテキストや運用上の責任を自動的に持っているわけではありません。各ドメインが持つ意味や優先順位が異なる場合、中央側がすべてをモデル化し、公開し、ガバナンスするまで待たされると、問題解決の速度は低下し、ローカルな知識はサイロ化したまま残ります。

データメッシュは、この問題に対して、中央集権を全面的に否定するのではなく、分散した所有権と共有された標準の両立を目指します。重要なのは、すべてのデータを中央で管理することではなく、ドメインごとの責任と横断的な相互運用性を両立する枠組みを作ることです。

## データメッシュとは何か

データメッシュは、単なる技術スタックや分散データ基盤ではなく、データに関する責任と価値創出の在り方を設計するアーキテクチャと組織モデルです。

メッシュ型アーキテクチャでは、組織を意味のあるドメインとして捉え、それぞれのドメインにそのデータの意味や業務文脈を理解する責任を持たせます。各ドメインはそのデータを作成し、品質を担い、利用可能な形で提供する。さらに、共有された標準と基盤機能によって、ドメイン間の利用と協調が可能になる構造を作ります。

これは、ストレージ手段だけではなく、組織的な協調の仕組みでもあります。データはアプリケーションの副産物ではなく、明確なオーナーと契約、責任を持つ資産として扱われます。重要なのは、あるデータ資産に対して誰が作成、品質、意味、提供可能性に責任を持つのかを明確にし、それを中央集権に依存しない形でスケールすることです。

## 4つの原則が作る統合モデル

データメッシュは、通常4つの原則で説明されます。これらは独立したアイデアではなく、ひとつの整合的なアーキテクチャを形成します。

### 1. ドメインオーナーシップ

最初の原則は、データはそれを生成し意味を理解しているドメインが所有すべきだという考え方です。ここでのドメインは単なるデータベースの境界ではなく、業務や運用上の意味を持つ明確な境界です。

この原則が重要なのは、ローカルな文脈が意味の質を決めるからです。営業ドメインは「適格な商談」が何を意味するか、いつ作成されるのか、どのイベントが正本かを知っています。配送ドメインは出荷状態の変化と例外の意味を理解しています。中央のプラットフォームチームが抽象的なデータ処理を理解していても、各ドメインの業務知識そのものに代わることはできません。

ドメインオーナーシップには次のような設計上の意味があります。

- データの所有が業務境界と責任を持つチームに従う
- 各ドメインが自分のデータの意味と正本を定義する
- 品質、鮮度、変更管理に対するローカルな説明責任が明確になる
- 共有ルールの中で、各ドメインが自分たちのデータを定義し、公開し、進化させる権限を持つ

ただし、この原則が成立するにはドメイン境界が明確である必要があります。境界が曖昧なままでは、所有権の概念はスローガンに終わってしまいます。

### 2. データをプロダクトとして扱うこと

2つ目の原則は、データは単なる副産物ではなく、利用者を前提にしたプロダクトとして扱うべきだという考え方です。データプロダクトは、利用者にとって理解しやすく、安全に使えるよう、契約やインターフェース、意味、期待値、ライフサイクル管理を備える必要があります。

「テーブルがある」ではなく「利用者が安全かつ効果的に使うために何を知る必要があるか」という視点に変わるのが、プロダクト思考の価値です。これには次のような情報が必要です。

- 所有者と責任者
- 発見可能性とアクセス方法
- スキーマと意味の定義
- 鮮度とレイテンシの期待値
- 品質保証と制約事項
- 利用者との契約や利用方法
- ライフサイクルと非推奨化の方針

データプロダクトは、単なる資産ではなく、生成者と利用者の境界にあるインターフェースです。利用者にとって使いやすい設計が組み込まれているからこそ、消費者の負担が減り、信頼につながります。

この原則は、技術と組織をつなぐ役割も持っています。データを運用しやすくするだけでなく、データと顧客や他部門との間に、より明確な契約関係を作ります。

### 3. セルフサービス型データ基盤

3つ目の原則は、セルフサービス型データ基盤です。データメッシュは、すべてのドメインが自前で独自の基盤を持つことを要求しません。むしろ、共通の基盤機能を提供するプラットフォームチームが、各ドメインが自律的に動ける土台を整えることを前提にしています。

セルフサービス基盤は、インフラの負担を減らし、共通的な運用を標準化する役割を持ちます。たとえば次のような機能が含まれます。

- データの公開と発見のためのインターフェース
- 保存と処理の再利用可能な機能
- アイデンティティとアクセス管理
- メタデータ収集とカタログ化
- リネージ取得と可観測性
- ポリシー適用のフック
- 品質検証やバリデーションのテンプレート

重要なのは、「すべてが各自で構築される」ことではなく、「共通の基盤が使いやすく、中央依存のなかで自律的な運用が可能になる」ことです。基盤は、各ドメインの意思決定を中央に戻すのではなく、共通の基盤を通じて自治と品質を両立させます。

この原則が重要なのは、ドメインの自律性がローカルの構築手段や手作業のガバナンスに依存してしまうと失敗するからです。セルフサービス型プラットフォームは、中央集権的なボトルネックをなくしつつ、共通の運用品質を維持する役割を担います。

### 4. フェデレーテッドガバナンス

4つ目の原則は、フェデレーテッドガバナンスです。分散型のデータアーキテクチャでは、すべての判断を一つの中央組織が担うことはできません。ガバナンスは、ドメインごとに分散しながら、全体として共有される標準と基準に従う形で機能する必要があります。

フェデレーテッドガバナンスとは、各チームが異なる意思決定を行いながらも、共通のポリシーや標準に沿って運用することを意味します。これには次のような要素が含まれます。

- ドメイン、所有者、データプロダクトの共通定義
- 発見性、リネージ、品質、ポリシーを表すメタデータモデル
- スキーマ、契約、アクセスパターンの相互運用性ルール
- データ分類とコンプライアンス基準
- スチュワードシップと例外対応の仕組み

ここで重要なのは、中央集権的な標準と中央集権的な実行を混同しないことです。ガバナンスの方針や最低限の統制は中央で定義できても、実際にその統制を執行するのはドメインやプラットフォームの実装側であることが多いからです。

このアーキテクチャがうまく機能するのは、完全な均質性ではなく、一貫性を確保するからです。各ドメインは異なる実装を持っていても、オーナーシップの意味、プロダクト契約、ポリシー、発見性の最低条件を揃えておく必要があります。

## メタデータは有効化基盤である

メタデータはデータメッシュにとって重要ですが、メタデータが主題そのものではありません。メタデータは、4つの原則をスケール可能に実現するための共有協調レイヤーです。

メタデータによって、各ドメインは自律的に動きながらも、組織全体で見えにくくなりません。メタデータを通じて、次のような情報がつながります。

- 所有者とドメイン境界
- プロダクト説明と責任範囲
- スキーマ、契約、バージョン管理
- リネージと影響範囲の分析
- 品質や鮮度のシグナル
- アクセスポリシーとコンプライアンス情報
- セマンティックな意味と共通用語

メタデータが弱いデータメッシュは、見た目だけが分散し、ローカルのサイロが増えるだけです。逆に、十分なメタデータがあれば、ドメイン横断で発見しやすく、判断しやすく、ガバナンスしやすく、進化しやすい設計になります。

したがって、メタデータは主役ではなく、データメッシュの実行可能性を支える補助機能として扱うべきです。重要なのは「何をカタログ化するか」ではなく、「ドメイン横断で発見され、信頼され、利用される条件をどう整えるか」です。

## アーキテクチャとしての運用モデル

データメッシュは、データの運用方法そのものを変えます。

### ドメインチームは第一級のデータ生成者になる

各ドメインは、自分たちのデータを生成し、その意味を責任を持って管理する主要な主体になります。これにより、業務現実とデータ表現のギャップが小さくなり、現場の知識がデータの価値に直結しやすくなります。データの意味と利用文脈が、業務の現場に近い場所で管理されるのです。

### プラットフォームチームは共通基盤を整える

プラットフォームチームは依然として重要ですが、その役割は変わります。すべてを中央で実行するボトルネックではなく、各ドメインが安全にデータプロダクトを提供できる共通基盤と標準を整えます。目的は、ドメインの自律性を促しながら、横断的な整合性を保つことです。

### 共通標準が断片化を防ぐ

このアーキテクチャが成立するには、標準は薄く、かつ適用可能である必要があります。各ドメインに強い一貫性を強制するのではなく、メタデータモデル、プロダクト契約、アイデンティティやアクセスの慣例、ポリシー要件などの最低限の共通条件を共有します。

このような共通標準があるからこそ、データメッシュは「分散したサイロの集まり」ではなく、つながったデータエコシステムになります。

## 利点とトレードオフ

データメッシュは、条件が整っている場合に強い効果を発揮します。

| 利点                         | アーキテクチャ上の意味                                   |
| ---------------------------- | -------------------------------------------------------- |
| オーナーシップの明確化       | 品質、意味、提供可能性に関する説明責任が明確になる       |
| 地域ごとの高速な提供         | 中央の待ち行列やボトルネックを減らせる                   |
| ドメイン知識との整合         | 現場の意味や利用状況により適したデータ製品を作りやすい   |
| 発見性の向上                 | メタデータと契約が共有されることで利用しやすくなる       |
| ガバナンスのスケーラビリティ | ドメインごとの自律性を保ちながら横断的な統制を可能にする |

一方で、トレードオフもあります。

- 強いドメイン自律性には、厳密なメタデータと標準インターフェースが必要になる
- 共有標準が弱いと、意味の揺れや断片化が起きる
- 各ドメインがローカル最適化に偏ると、全体としての相互運用性が失われる
- 基盤層が適切に設計されないと、中央集権型の依存が再び顕在化する

つまり、データメッシュは万能の設計ではなく、規模と責任の境界が明確な組織でこそ意味を持つ設計です。

## どんな場合に適しているか

データメッシュが適しているケースは次のとおりです。

- 組織内に複数の意味のあるドメインがあり、それぞれに独自の業務コンテキストがある
- 中央のプラットフォームがボトルネックになっており、ドメインごとの迅速な提供が難しい
- 共通標準を維持しながらも、各ドメインの自律性を高めたい
- メタデータ、契約、基盤機能を整備できる成熟度がある
- データの責任と提供義務を明確にしたい

## 向かない場合

一方で、次のような場合にはデータメッシュが適さないことがあります。

- 組織が小さく、明確なドメイン境界がまだ定義されていない
- 中央統制が必要な法務、セキュリティ、運用上の整合性が強い
- 各ドメインがデータプロダクトと契約を持つ成熟度に達していない
- 問題が技術の集約ではなく、組織設計の成熟度の向上にある

このような場合は、より中央集権型または共通基盤型のアーキテクチャが、簡潔で効果的な選択肢になることがあります。

## まとめ

データメッシュは、4つの原則――ドメインオーナーシップ、データをプロダクトとして扱うこと、セルフサービス型データ基盤、フェデレーテッドガバナンス――を軸にした、ドメイン志向のデータアーキテクチャです。

その中心的な考え方は、データを分散したいから分散するのではなく、組織の実際の責任境界と知識の境界に合わせて、責任と相互運用性を両立させることにあります。データメッシュは、各ドメインが自分のデータを責任を持って提供しながら、共有された標準、基盤機能、メタデータによって組織全体の信頼と発見性を支える設計です。

うまく設計されたデータメッシュは、データを中央依存の資産としてではなく、明確な契約と責任を持つプロダクト群として扱う仕組みを作ります。大規模でドメインが多い組織において、これは重要なアーキテクチャパターンです。
