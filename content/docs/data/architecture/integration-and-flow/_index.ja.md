データ統合は、一つの境界で生成された情報を別の境界で利用できるようにシステムを接続します。移動メカニズムは、遅延、結合度、整合性、障害時の振る舞い、再生可能性、接続を運用する責任主体を決めます。そのため、単なるパイプライン実装ではなく、アーキテクチャ上の意思決定です。

## 境界から始める

生成側と利用側、権威あるソース、転送データの意味、双方が約束できるサービスを特定し、次を検討します。

- 利用側が求めるのは現在状態か、変更通知か、履歴の再構築か
- 技術的に可能な遅延ではなく、価値のある遅延はどの程度か
- 利用側は生成側の可用性に依存できるか
- 重複、順序入れ替え、一時的な不整合を許容できるか
- 処理を再生または監査可能にする必要があるか
- セキュリティ、プライバシー、データ所在、オーナーシップの境界を越えてコピーできるか

## データ移動パターン

### バッチとファイル転送

バッチは、スケジュールに従って境界付きのスナップショットまたは増分を抽出します。ファイルは持ち運びや検査が容易な配信成果物で、接続されていない境界も越えられます。

数分から数時間の遅延を許容でき、データ量が多く、照合が重要な場合に適します。完了点が明確なため、再実行と監査が容易です。一方、大きな処理窓は鮮度の空白と負荷集中を生み、不明確な増分条件は重複や欠落を招きます。

### ETL と ELT

**ETL** はターゲットへロードする前に変換します。永続化前に公開範囲を最小化し、ターゲット契約を強制できます。**ELT** はソースに近い形でロードし、スケーラブルな分析システム内で変換するため、柔軟な再処理が可能です。

これは時代の新旧ではなく、配置の選択です。機密フィールドをロード前に検証・最小化し、その後ウェアハウスで分析モデルを構築するフローもあります。計算資源の拡張場所、生データの保存可否、ロジックのテスト方法、オーナーを比較します。

### API

API は、境界の明確なドメインクエリまたは操作を要求時に公開します。生成側が管理するインターフェースを維持し、データベースへの無制限なアクセスを避けられます。

対話的な参照や業務統合に適しますが、利用側を実行時可用性、クォータ、バージョン動作に結び付けます。レコード単位の API による一括抽出は非効率になりがちです。ページネーション、キャッシュ、冪等性、レート制限、エラーの意味を明示します。

### 複製と変更データキャプチャ

複製は、局所性、可用性、ワークロード分離のためにコピーを維持します。**変更データキャプチャ（CDC）** は、一般にデータベースログからコミット済み変更を読み取り、挿入、更新、削除を下流へ出力します。

CDC は、完全抽出を繰り返す方法よりソース負荷と遅延を下げられます。一方、物理データベースの詳細、トランザクション順序、スキーマ変更、初期スナップショット、削除処理を公開します。CDC レコードはストレージ変更を表すもので、自動的に安定したドメインイベントになるわけではありません。

### メッセージング

キューとメッセージブローカーは、生成側の実行と利用側の処理を分離します。非同期処理、バッファリング、再試行、独立したスケーリングを支えます。

確認応答、再試行、デッドレター処理、冪等性、順序の範囲、保持、バックプレッシャーを設計します。「Exactly Once」という主張は、ブローカー内のトランザクションだけでなく、副作用全体で評価すべきです。

### イベントストリーミング

イベントストリームは、複数の利用側が継続処理し、保持期間内なら再生できる順序付きシーケンスを保持します。リアルタイムの射影、監視、統合、増分分析を支えます。

永続履歴と利用側の独立性を得られる一方、スキーマ互換性、パーティショニング、イベント時刻処理、状態管理、運用可観測性が必要です。イベントの意味と、ログが正本、派生物、単なる転送手段のどれであるかを決めます。

### フェデレーションと仮想化

フェデレーションは、利用側の基盤に管理コピーを保存せず、所有元システムのデータを照会します。データ所在、自律性、現在データへの迅速なアクセスを支えられます。

クエリ時統合は、リモート側の遅延、可用性、同時実行制限、意味の差異を引き継ぎます。プッシュダウンとキャッシュは性能を改善できますが、ポリシーと鮮度を複雑にします。リモートシステムが安定したスキーマ、予測可能なサービス、互換性のあるアイデンティティとポリシーを提供する場合に効果的です。

## 選択肢の比較

| パターン               | 代表的な遅延 | 結合                           | 整合性                             | 再生可能性                               | 運用上の課題                           |
| ---------------------- | ------------ | ------------------------------ | ---------------------------------- | ---------------------------------------- | -------------------------------------- |
| バッチ／ファイル       | 分〜日       | 実行時は低いが契約には結合     | スナップショットまたは期間単位     | 配信物を保持すれば高い                   | スケジューリング、増分、照合           |
| API                    | リクエスト時 | 実行時依存が高い               | 生成側が示す現在状態               | 呼び出しを記録しない限り低い             | 可用性、クォータ、バージョン管理       |
| 複製／CDC              | 秒〜分       | ソースの変更モデルに結合       | コピーは結果整合                   | ログとスナップショットを保持すれば高い   | スキーマ変更、順序、再同期             |
| メッセージング         | 秒以下       | 実行は疎結合                   | 通常は結果整合                     | 保持とデッドレター設計による             | 再試行、重複、バックプレッシャー       |
| イベントストリーミング | ミリ秒〜秒   | 契約には結合するが利用側は独立 | 結果整合またはストリーム定義に従う | 保持履歴内では高い                       | 状態、パーティション、遅延データ、再生 |
| フェデレーション       | クエリ時     | リモート依存が高い             | リモートの現在ビューを読む         | 再現にはスナップショットまたはログが必要 | リモート性能、ポリシー、障害           |

これらは傾向であり、保証ではありません。日次 API 取得はバッチとして動作し、コンパクション済みストリームは現在状態を表し、厳密に管理された構成の複製データベースは強い保証を提供できます。

## ETL、イベント、CDC は異なる抽象化

ETL パイプラインは、ターゲットに向けてデータをどう抽出・変換するかを表します。CDC は物理状態の変更をどう取得するかを表します。ドメインイベントは業務またはシステムで何が起きたかを表します。一つの実装で CDC レコードをドメインイベントへ変換し、後で分析テーブルへ変換することはできますが、各段階の契約とオーナーは異なります。

抽象化を分けることで、下流の利用側が意図せずソース内部へ依存することを防げます。

## 障害と変更を設計する

- 重要なフローに、オーナー、スキーマまたは契約、鮮度期待値、観測可能な完了または遅延シグナルを設ける
- バッチ識別子、イベントオフセット、API リクエスト、ターゲットレコードをまたいで相関とリネージを維持する
- 再試行を冪等にするか、重複した副作用を検出・修復可能にする
- 本番投入前に、初期ロード、再同期、削除、遅延到着、スキーマ進化を定義する
- 遅い利用側、利用不能なソース、不正メッセージ、期限切れ認証情報、非互換変更など、オーナーシップ境界での障害をテストする
- リスクに応じて、派生状態を権威あるソースと照合する

実装はデータエンジニアリングの領域ですが、許容する障害モードと責任分担はアーキテクチャの領域です。
