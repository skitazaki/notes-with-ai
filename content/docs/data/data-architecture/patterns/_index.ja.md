データアーキテクチャパターンは、責務、保存、移動、オーナーシップの繰り返し現れる構成です。完成済みの設計ではなく、構造を認識するための道具として使います。実際の環境では複数パターンを組み合わせます。また、同じ名称がストレージ技術、処理モデル、統合スタイル、組織モデルのいずれかを表す場合があります。

## 分類軸を一つに潰さない

ウェアハウス、レイク、レイクハウスは主に分析データの保存・処理構成を表します。イベント駆動とストリーミングは、連携と計算の方法を表します。データメッシュは、ドメインオーナーシップ、データプロダクト、セルフサービス基盤、フェデレーテッドガバナンスを中心とする運用モデルです。「中央集約」と「フェデレーテッド」は、権限または実行機能の配置を表します。

これらの次元は共存できます。ドメイン指向の組織が共通レイクハウスを通じてプロダクトを公開し、変更をイベントとして配布し、 [セマンティック層](/ja/docs/data/metadata/semantic-layer/) を通じて統制された指標を提供することもできます。

## 中央集約型分析アーキテクチャ

多数のソースから得たデータを、中央運用のウェアハウスまたは分析基盤へ統合します。共通モデルと統制によって、全社レポーティングとドメイン横断分析を支えます。

一貫性、統合指標、専門知識の集約が重要な場合に有効です。一方、中央チームが提供上のボトルネックになり、モデリングがドメイン文脈から離れ、中央基盤が大きな障害・協調境界になる可能性があります。

## ハブアンドスポーク

共通ハブが統合、保存、ガバナンス、正規データを提供し、スポークがドメイン、事業部門、ワークロードを担います。ハブは基盤の重複を減らし、ドメイン横断ビューを支えます。スポークはローカルな最適化を保ちます。

難しいのは、何をハブに置くかです。中央ロジックが多すぎるとモノリスを再現し、少なすぎるとアイデンティティ、意味、統制が不統一になります。ハブが物理データ、メタデータ、交換、ポリシー、共通基盤サービスのどれを所有するか定義します。

## 共通データプラットフォーム

プラットフォームチームが、取り込み、保存、処理、オーケストレーション、カタログ、セキュリティ、品質、提供の再利用可能な機能を提供します。生成側と利用側のチームは、各自でインフラを組み立てず、これらの機能を利用します。

多くのチームに共通ニーズがあり、セルフサービスによって調整負荷を減らせる場合に適します。「セルフサービス」が実質的にチケットキューであったり、異なるワークロードを一つの経路へ強制したりすると失敗します。プラットフォームインターフェースを、利用者、サービス期待値、採用戦略を持つプロダクトとして扱います。

## ウェアハウス、レイク、レイクハウス

- **ウェアハウス**は、管理された分析テーブル、クエリ性能、統制されたモデリングを重視します。
- **レイク**は、オブジェクトストレージまたは分散ストレージへの多様なデータの大規模保持と、複数の処理方法を重視します。
- **レイクハウス**は、レイク型ストレージにテーブルトランザクション、スキーマ管理、分析アクセスを加えます。

階層またはワークロード境界を通じて、これらは共存できます。テーブルの意味、カタログの権威、エンジン互換性、ワークロード分離、ガバナンス、運用成熟度、総コストを評価します。「オープン形式」は可搬性を高められますが、カタログ、セキュリティモデル、SQL 動作を同一にするわけではありません。

## イベント駆動アーキテクチャ

生成側が意味のある状態変化を事実として公開し、生成側が各処理を調整しなくても利用側が反応できるようにします。独立した利用側と準リアルタイムのワークフローを実現できます。

自律したシステム間の統合に適します。一方、永続的なイベント契約、明確な意味、冪等性、相関、順序期待値、再生戦略、端から端までの可観測性が必要です。イベントは、特別な理由がない限り、生成側の内部データベースログではなくドメイン上の事実を表すべきです。

## ストリーミングアーキテクチャ

境界付きバッチを待たず、連続するレコードを増分処理します。状態を持つプロセッサは、ウィンドウ集約、ストリーム結合、パターン検出、提供用ストアの更新を行えます。

低遅延の判断と継続的に変化する状態に適します。運用上は、バックプレッシャー、チェックポイント、遅延・順序外イベント、状態増大、デプロイ互換性、再生が複雑になります。ストリーミング転送を採用しても、有用な処理が夜間ジョブを待つなら、ストリーミングアーキテクチャとはいえません。

## Lambda と Kappa

**Lambda アーキテクチャ**は、完全な再計算を行うバッチ経路と、低遅延結果を生む高速経路を用意し、提供時に統合します。完全性と遅延の歴史的な対立を解決しますが、ロジックと運用を重複させます。

**Kappa アーキテクチャ**は、主となるストリーミング経路を使い、保持されたログの再生によって再処理する考え方です。イベント履歴が完全で、ストリーム処理が必要な再計算を支えられる場合、コードの重複を減らせます。長期保持、状態移行、参照データ、訂正は依然として重要な制約です。

## フェデレーテッドアーキテクチャ

データ、計算、権限を分散したまま、共通プロトコルと統制によってアクセスを調整します。自律性、データ所在、ワークロードの局所性を維持できます。クエリフェデレーションと組織的フェデレーションは関連しますが、同じではありません。前者は実行を分散し、後者は意思決定権を分散します。

リモート側の可用性、性能、アイデンティティ、意味の整合、ポリシー評価、障害責任がアーキテクチャ上の課題になります。フェデレーションは中央設計の不在ではなく、明示的な合意によって機能します。

## ドメイン指向アーキテクチャとデータメッシュ

ドメイン指向アーキテクチャは、業務と運用の文脈を持つチームの近くに責任を置きます。 [データメッシュ](/ja/docs/data/metadata/data-mesh/) は、ドメインオーナーシップ、 [データプロダクト](/ja/docs/data/metadata/data-products/) 、セルフサービス基盤、 [フェデレーテッドガバナンス](/ja/docs/data/metadata/federated-governance/) を通じて、これをより広い社会技術的モデルとして定義します。

中央のボトルネックを減らし、文脈に基づくオーナーシップを改善できます。一方、相互運用可能なインターフェース、共通ポリシー、プロダクト発見、組織能力が一層必要になります。データセットを「プロダクト」と呼び替えたり、ドメイン名を割り当てたりするだけでは実装できません。

## 論理的な中央集約と物理的な中央集約

論理的に統合された体験に、一つの物理ストアは必須ではありません。カタログ、セマンティック層、アクセスゲートウェイ、フェデレーテッドクエリによって、分散資産を一貫して提示できます。反対に、すべてのファイルを一つのバケットへ置いても、共通の意味、ガバナンス、オーナーシップは生まれません。

次の問いを分離します。

- データを物理的にどこで保存・処理するか
- メタデータ、アイデンティティ、ポリシー、意味をどこで協調させるか
- 誰が意思決定権と運用責任を持つか
- 利用者にどのようなインターフェースを提供するか

## パターンの比較

| パターン             | 主な強み                                     | 主な課題                             |
| -------------------- | -------------------------------------------- | ------------------------------------ |
| 中央集約型分析       | 一貫性とドメイン横断分析                     | 中央のボトルネックと文脈の喪失       |
| ハブアンドスポーク   | 共通基盤とローカル特化の両立                 | ハブ境界の定義と統制                 |
| 共通プラットフォーム | 再利用とセルフサービス                       | プロダクト規律とワークロードの多様性 |
| イベント駆動         | 疎結合と迅速な反応                           | 契約、配信の意味、可観測性           |
| ストリーミング       | 低遅延の増分計算                             | 状態を持つ継続運用と再生             |
| フェデレーテッド     | 自律性、局所性、データ所在                   | 境界を越える意味、ポリシー、障害対応 |
| ドメイン指向         | 文脈に基づくオーナーシップと組織規模への対応 | 相互運用性と組織的な準備             |

制約と品質属性に基づいてパターンを選び、その組み合わせを明示します。移動メカニズムについては [データ統合とフロー](../integration-and-flow/) へ進むか、 [データアーキテクチャのハブ](../) に戻ってください。
