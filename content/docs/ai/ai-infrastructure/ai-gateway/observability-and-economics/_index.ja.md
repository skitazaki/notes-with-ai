AI システムには、通常のサービステレメトリに加え、モデル利用、ツール活動、エージェント委任、コストに関する証跡が必要です。ゲートウェイはこれらの通信を共通境界で観測できるため、有用な観測点になります。ただし、その視野は部分的です。アプリケーションの成果、モデル品質、業務価値は、それらを所有するシステムのデータと結び付ける必要があります。

## 要求トレースからエージェントトレースへ

通常の要求トレースは、サービス、ルート、状態、レイテンシを記録します。AI トレースには、プロバイダー、モデル、デプロイ、最初のトークンまでの時間、ストリーム時間、入力・出力トークン、キャッシュ判断、再試行、フォールバック、ポリシー結果も含まれます。エージェントトレースは、さらに MCP ツール呼び出しと A2A タスクまで連鎖を広げます。

相関情報は、開始要求、モデル呼び出し、ツール実行、承認、リモートエージェントのタスク、返却された成果物の関係を維持します。無制限のプロンプトや推論過程を記録する必要はありません。安定した ID と構造化イベントの方が、完全なペイロード取得より安全な運用証跡になることが一般的です。

## なぜトークンを観測するのか

要求数は AI 消費量の指標として不十分です。短い質問から1文を返す要求もあれば、長い会話履歴、ツール定義、検索文書を送り、大きな応答を生成する要求もあります。トークンは業務成果そのものではありませんが、処理・生成したテキスト量を比較するための有用な共通指標です。

ゲートウェイでは、通常、次の利用量を観測または受信できます。

| トークン指標               | 一般的に含まれるもの                                                                                                   | 増加する理由                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 入力トークン               | システム・アプリケーション指示、利用者メッセージ、会話履歴、ツールスキーマ、検索コンテキスト、メモリ、過去のツール結果 | 履歴の長期化、ツール増加、大きな検索結果、指示の反復、エージェントループ |
| キャッシュ済み入力トークン | プロバイダーが再利用可能と認識した入力                                                                                 | 安定したプロンプト先頭部、反復するツールスキーマ、共通参照コンテキスト   |
| 出力トークン               | プロバイダーが返す生成テキストまたは構造化出力                                                                         | 冗長な回答、大きな生成物、ツール引数、弱い停止条件                       |
| 推論・内部利用トークン     | 一部のプロバイダーやモデル種別が報告する追加計算量                                                                     | 難しいタスク、高い推論設定                                               |

プロバイダーごとに利用量フィールドと課金規則は異なります。キャッシュ済み入力を分けるもの、推論関連の利用量を報告するものがあります。マルチモーダル入力、画像、音声、ファインチューニング、ホスト型ツール、バッチ処理では、テキストトークン以外の単位も使われます。すべてを1つの合成トークン数へ押し込まず、プロバイダーが報告した元の利用区分を保持します。

### コンテキストの増加と増幅

会話型・エージェント型システムでは、入力増加が主要なコスト要因になりがちです。新しい利用者メッセージが短くても、実際の入力には過去の全ターン、システムプロンプト、多数のツールスキーマ、検索文書、メモリ、過去のツール結果が含まれます。エージェントが5回モデルを呼び出し、そのたびに大部分のコンテキストを送ると、画面に見える利用者メッセージだけでなく、反復処理にもコストがかかります。

たとえば、300トークンの利用者要求に、1,500トークンの指示、2,500トークンのツール定義、5,000トークンの検索結果、2,700トークンの履歴が加わると、モデル入力は12,000トークンになります。同様のモデル呼び出しを4回行えば、出力を除いても入力は約48,000トークンに達します。トークンテレメトリは、要求数や利用者に見える文章だけでは分からないアーキテクチャ上の消費を示します。

トークン数はあくまで代理指標です。モデル消費、レイテンシ、コンテキスト圧力、概算コストを説明できますが、正しさ、顧客価値、タスク成功を測るものではありません。

## 利用量からコストへ

コスト計算はプロバイダー画面の数値を転記するのではなく、再現可能な処理として設計します。

1. **要求を計測する。** プロバイダー、モデルまたはデプロイ、リージョン、時刻、入力区分、出力区分、キャッシュ状態、トークン以外の利用単位を記録します。
2. **配賦軸を付ける。** 認証済みテナントと実行主体に加え、信頼できるプロジェクト、プロダクト、環境、ワークフロー、コストセンターのメタデータを付けます。
3. **単価を解決する。** 要求時刻に有効な版管理済み単価表を選びます。公開単価、契約割引、予約容量、社内振替価格を含み得ます。
4. **直接費を計算する。** 各利用区分を対応する単価と掛け合わせます。出力単価を入力に使ったり、単価が異なるキャッシュ済み・未キャッシュ入力を同一に扱ったりしません。
5. **共通費を明示的に加える。** ゲートウェイ運用、オブザーバビリティ、評価、ベクトル検索、プラットフォーム支援などを、文書化した規則で別途配賦します。
6. **台帳へ保存する。** 元の利用量、単価表の版、計算額、通貨、配賦キー、計算ロジックの版を保持し、監査と再計算を可能にします。

テキストモデルの単純化した式は次のとおりです。

```text
モデル直接費 =
    （未キャッシュ入力トークン ÷ 単価単位 × 未キャッシュ入力単価）
  + （キャッシュ済み入力トークン ÷ 単価単位 × キャッシュ済み入力単価）
  + （出力トークン ÷ 単価単位 × 出力単価）
  + その他の計量課金
```

100万トークン当たりの単価なら、単価単位は `1,000,000` です。

### 計算例

特定プロバイダーの実価格ではなく、次の社内単価表を仮定します。

| 利用区分             |          観測量 |      例示単価 |     コスト |
| -------------------- | --------------: | ------------: | ---------: |
| 未キャッシュ入力     | 180,000トークン | $2.00 / 100万 |     $0.360 |
| キャッシュ済み入力   | 120,000トークン | $0.20 / 100万 |     $0.024 |
| 出力                 |  30,000トークン | $8.00 / 100万 |     $0.240 |
| **モデル直接費合計** |                 |               | **$0.624** |

このワークロードへゲートウェイ、テレメトリ、プラットフォームの共通費 $0.076 を配賦すると、完全配賦額は $0.700 です。直接費 $0.624 と共通費 $0.076 を分離すると、プロバイダー消費と社内配賦方針の両方を説明できます。

## 配賦軸

配賦は単一の階層ではありません。同じ台帳レコードから、組織的な内訳と横断的な分析の両方を作る必要があります。

### 階層的な内訳

一般的な所有経路は次のようになります。

```text
テナント
  └─ プロジェクトまたはコストセンター
       └─ プロダクトまたはアプリケーション
            └─ 環境
                 └─ ワークフローまたは機能
                      └─ 利用者またはサービス ID
```

- **テナント**は分離、外部請求、企業単位の予算を支えます。
- **プロジェクトまたはコストセンター**は、消費を予算と責任を持つ実行組織へ結び付けます。
- **プロダクトまたはアプリケーション**は、顧客向け・社内向けのどの能力が予算を消費するかを示します。
- **環境**は、本番利用と開発、テスト、評価を分離します。
- **ワークフローまたは機能**は、文書要約、問い合わせ回答、コードレビューなどの用途を区別します。
- **個人またはサービス ID**は、ID ポリシーが許す場合に調査とショーバックを支えます。個人単位の報告を無制限な監視にしないよう、目的、アクセス、保存期間を明確にします。

### 横断的な分析

同じレコードを、モデル、プロバイダー、リージョン、エージェント、ツール、要求種別、データ分類、キャッシュ結果、レイテンシ区分、成功状態、実験ごとにも集計できます。所有階層だけでは答えられない問いを扱えます。

- 全プロダクトを通じ、サポート解決1件当たりのコストが最も高いモデルはどれか。
- 複数テナントでコンテキストを繰り返し増幅しているツールやエージェントはどれか。
- 開発・評価トラフィックのうち、本番向け価格のモデルを使っている割合はどれだけか。
- 再試行を含む実効コストが最も高いリージョンやプロバイダーはどこか。
- プロンプトキャッシュや小型モデルへの切り替えが最も有効な場所はどこか。

配賦メタデータは、可能な限り認証済み ID、デプロイ設定、統制されたレジストリから取得します。呼び出し元が任意のテナントやコストセンターを申告できると、チャージバックの信頼性が失われます。

### 配賦台帳の例

以下は、1つのデータセットから複数の集計を作る例です。金額は例示です。

| テナント  | プロジェクト   | プロダクト         | 実行主体       | ワークフロー   | モデル区分 | 直接費 | 共通費 |   合計 |
| --------- | -------------- | ------------------ | -------------- | -------------- | ---------- | -----: | -----: | -----: |
| Northwind | カスタマー運用 | サポート Copilot   | `user-184`     | 回答案の生成   | 汎用       | $0.624 | $0.076 | $0.700 |
| Northwind | カスタマー運用 | サポート Copilot   | `user-227`     | ケース要約     | 小型       | $0.180 | $0.030 | $0.210 |
| Northwind | ナレッジ基盤   | 検索アシスタント   | `search-agent` | 根拠付き検索   | 汎用       | $0.410 | $0.060 | $0.470 |
| Contoso   | 開発者体験     | コードアシスタント | `user-991`     | コードレビュー | 推論       | $1.850 | $0.150 | $2.000 |

財務部門は、この行から Northwind に $1.38、Contoso に $2.00 を集計できます。カスタマー運用プロジェクトとサポート Copilot には、この例では $0.91 が割り当てられます。プラットフォームチームは所有境界を横断し、汎用、小型、推論モデルを比較できます。プロダクト所有者は、サポート Copilot を回答案とケース要約に分解できます。権限を持つ運用者は、個人 ID を予算管理の中心にせずに、必要な場合だけ実行主体を調査できます。

| 指標                           | 運用上の問い                                                     |
| ------------------------------ | ---------------------------------------------------------------- |
| 最初のトークンまでの時間       | 有用な出力が始まるまでどの程度かかるか                           |
| エンドツーエンド時間           | 対話全体が完了するまでどの程度かかるか                           |
| 入力・キャッシュ・出力利用量   | どのワークロードがモデル容量を使い、どこでコンテキストが増えるか |
| ツール・エージェント呼び出し   | 推論以外のどこへ処理が分岐するか                                 |
| 再試行・フォールバック率       | どの依存先やポリシーが不安定か                                   |
| テナント・ワークフロー別コスト | 誰が何の目的で予算を消費するか                                   |

## 次元数の多さ、プライバシー、保存期間

エージェント ID、ツール名、モデル版、テナント、セッション、タスク ID は、取り得る値の種類が非常に多い、高カーディナリティ（high cardinality）のテレメトリを生みます。次元の値が際限なく増えると、観測コストが上がり、メトリクス基盤が不安定になります。値の種類を限定できる次元にはメトリクス、詳細イベントにはトレースやログ、探索にはサンプリング・集約ビューを使います。

プロンプト、応答、ツール引数、結果には、個人情報、機密情報、規制対象データが含まれ得ます。既定のテレメトリでは内容を除外またはマスキングし、テナント分離と適切な保存期間を適用します。デバッグ用の取得は、明示的で期間限定、アクセス制御され、運用者に可視であるべきです。

## 経済性を信頼性・品質へ結び付ける

最安のルートでも、再試行、レイテンシ、人手レビュー、失敗が増えれば経済的とは限りません。ゲートウェイデータはルートと利用量をサービス水準へ結び付け、アプリケーション評価は品質と業務成果を補います。トークン単価より、成功したタスク1件当たりのコストの方が有用な場合があります。

## 配賦から最適化へ

コスト管理は、成果を損なわずに技術判断を改善する場合に価値があります。

1. **基準値を作る。** 配賦軸ごとにトークン、直接費、共通費、レイテンシ、成功率、品質を計測します。
2. **増幅箇所を見つける。** 反復するコンテキスト、過大な検索結果、使わないツールスキーマ、不要なエージェント反復、冗長な出力、再試行、低いキャッシュヒット率を特定します。
3. **適切な分母を選ぶ。** 要求単価だけでなく、成功タスク、解決ケース、生成物、アクティブテナント当たりのコストを比較します。
4. **限定された変更を行う。** 履歴の削減、メモリの要約、ツールの絞り込み、検索改善、安定した先頭部のキャッシュ、単純タスクの小型モデルへのルーティング、出力上限、再試行ループ削減を行います。
5. **結果を検証する。** コストとレイテンシが改善し、成功率、安全性、品質が基準内にあることを確認します。
6. **ポリシーへ反映する。** 実証した改善を、予算、アラート、ルーティング規則、コンテキスト上限、プラットフォーム既定値へ変えます。

トークン観測はこのループをつなぎます。コスト変化が、トラフィック量、コンテキスト増加、出力長、キャッシュ、モデル選択、ワークフロー分岐のどれによるかを示します。組織がコストを管理するのは、無制限な消費が有用なプロダクトの経済性を損なうためです。トークンを観測するのは、モデル消費がどこで発生したかを示す、実行可能な代理指標だからです。

## まとめ

AI ゲートウェイは、プロバイダーとプロトコルを横断するテレメトリの強い観測点です。元の利用区分と因果関係を記録し、版管理された単価表を適用し、統制された配賦軸を付けることで、直接費と共通費を説明できます。階層的な所有ビューと横断的な運用ビューは、同じ監査可能な台帳から作るべきです。

トークンは、要求数では見えないコンテキスト増幅とモデル消費を示します。ただし代理指標なので、最適化ではレイテンシ、信頼性、品質、成功成果へ結び付けます。配賦で無駄を特定し、限定的な変更で削減し、効率化が価値や安全性を損ねていないことを評価するとき、コスト管理は継続的なエンジニアリングのフィードバックループになります。
