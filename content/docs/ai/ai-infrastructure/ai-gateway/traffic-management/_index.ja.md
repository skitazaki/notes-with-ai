AI トラフィック管理は、一般的な分散システムの制御を、処理時間、コスト、失敗時の振る舞いが特有なワークロードへ適用します。ゲートウェイはルーティングと保護を一貫させますが、処理がストリーミングか、アプリケーションレベルで状態を持つか、高コストか、副作用を発生させるかを理解する必要があります。

## ルーティングと容量

ルーティングでは、モデル能力、プロバイダーの健全性、リージョン、テナント、レイテンシ目標、データポリシー、コンテキスト長、予算を考慮できます。負荷分散は同等なデプロイ間でトラフィックを分けますが、モデル選択は異なる結果を生み得るバックエンドから選びます。両者を分離すると、ポリシーを説明し試験しやすくなります。

レート制限は瞬間的な容量を守り、クォータと予算は長期間の消費を制限します。呼び出し元、テナント、モデル、ツール、エージェント ID ごとに適用できます。2つの要求が消費するトークン、計算資源、ツール資源は大きく異なるため、要求数だけでは不十分です。

## AI ゲートウェイとモデルルーター

モデルルーターは主に、どのモデルが要求を処理すべきかを判断します。タスクの種類、品質、レイテンシ、価格、可用性、ポリシーなどに基づいてモデルを選択します。

AI ゲートウェイは、AI 関連トラフィックをどのように接続し、保護し、統制し、観測し、ルーティングするかという、より広い問いを扱います。モデル選択はゲートウェイ境界内の1機能、ゲートウェイから呼び出す独立したサービス、またはゲートウェイが所有しないアプリケーションロジックとして実装できます。この区別を保つことで、ルーティングアルゴリズムが要求経路に存在するという理由だけで、認証情報、監査、ツールガバナンスなど、あらゆるプラットフォーム上の関心事を抱え込むことを防げます。

## 障害とフォールバック

タイムアウト、再試行、サーキットブレーカー、フォールバックは異なる制御です。タイムアウトは待機時間を制限し、再試行は操作を繰り返し、サーキットブレーカーは異常な依存先への送信を止め、フォールバックは依存先やモデルを変更します。

副作用を持たない推論要求は再試行できる場合がありますが、追加コストが発生し、回答も変化し得ます。ツールやエージェントの呼び出しには明示的な冪等性が必要です。応答を受信できなかっただけで再実行すると、注文、メッセージ、ワークフローを重複させる可能性があります。

フォールバックも意味を変えます。別のモデルは、同じコンテキスト長、ツールスキーマ、モダリティ、ポリシー、品質目標を満たさないかもしれません。すべてのエンドポイントを同等とみなさず、許容可能な代替をポリシーで定義します。

## ストリーミングと長時間処理

ストリーミング推論では、バックプレッシャー、キャンセルの伝播、アイドル・総時間の上限、最初のトークンまでの時間を扱います。ストリームをバッファリングすると、レイテンシ目標を損ない、メモリ使用量を増やします。

エージェント処理は HTTP 接続より長く続く場合があります。永続的なタスク状態は、処理を所有するエージェント、プロトコル実装、ワークフローシステムに置きます。ゲートウェイはタスクへのアクセスを認可し、ポーリングや購読をルーティングし、テレメトリを関連付けますが、不適切なトランスポートを補うために不透明なワークフロー状態を持つべきではありません。

## デプロイメントと運用モデル

ゲートウェイの設計には、どのアプリケーションがゲートウェイ境界を共有するか、誰がポリシーと設定を所有するか、データプレーンのインスタンスをどこに配置してトラフィックを処理するかという、独立した判断があります。コントロールプレーンを集中管理してもランタイムを1つにする必要はなく、複数のゲートウェイが共通のポリシー基盤から設定を継承することもできます。

### 共有 AI ゲートウェイ

共有 AI ゲートウェイは、複数のアプリケーションやチームに共通の論理的な入口を提供します。統合の重複を減らし、プロバイダーの認証情報、ルーティングポリシー、テレメトリ、調達、コスト配賦の一貫性を高められます。

一方、この共有境界は共通の依存関係にもなります。容量、リージョン配置、設定の展開、障害分離は、集約されたワークロードに合わせる必要があります。論理的には1つのゲートウェイでも、単一のグローバルランタイムではなく、リージョンやワークロードごとに複数のデータプレーンインスタンスを配置できます。

### 環境・ドメイン別の連合ゲートウェイ

連合ゲートウェイは、環境、事業ドメイン、リージョン、チーム、信頼ドメインごとに、独立した範囲の境界を設けます。これにより障害範囲を限定し、データレジデンシーに対応し、ローカルな所有権やドメイン固有のポリシーを持たせられます。

一方、連合構成では、設定、アップグレード、オブザーバビリティのパイプラインが増えます。共通ポリシーテンプレート、協調された設定、連合テレメトリを利用すれば、すべてのトラフィックを1つの共有ゲートウェイへ集めずに、組織全体の要件を維持できます。

### Kubernetes ネイティブなデプロイメント

Kubernetes は、独立した所有モデルではなく、デプロイメントと設定の選択肢です。共有型または連合型のゲートウェイで、 [Kubernetes Gateway API](https://gateway-api.sigs.k8s.io/) をゲートウェイ、リスナー、ルートの役割指向のモデルとして利用できます。AI 対応の拡張や実装固有のポリシーによってモデルやエージェントの意味を追加し、既存のプラットフォームエンジニアリングの運用へ統合できます。Gateway API との統合は運用の一貫性を高めますが、標準 API 自体がトークン計測、プロンプトポリシー、MCP 認可などの AI の振る舞いを定義するわけではありません。

## まとめ

AI トラフィック管理は、ルーティング、制限、回復性、ライフサイクルを理解したトランスポート処理を組み合わせます。モデル選択と負荷分散を区別し、安全でない再実行を避け、フォールバック条件を明示し、長時間タスクの所有権をゲートウェイ外に保つことが重要です。
