AI ゲートウェイは、モデル、ツール、エージェント、API のトラフィックが信頼境界を越える場所にあります。一貫した強制点として有用ですが、ID、同意、業務権限の源泉になるわけではありません。接続に関係するコンテキストを保持し、決定を強制することが役割です。

## ID と認証情報

認証は呼び出し元を確立し、認可はその呼び出し元が特定の操作を実行できるかを決めます。エージェントシステムでは、実行するエージェントの ID と、作業を委任した利用者またはサービスの両方が必要です。1つのゲートウェイ認証情報へ統合すると、ポリシーと監査証跡が弱くなります。

ゲートウェイは、範囲を限定した上流認証情報を交換または注入し、プロバイダーやツールの秘密をアプリケーションから分離できます。認証情報は、対象、テナント、操作、有効期間に結び付けます。モデル API キー、MCP 認可トークン、A2A 呼び出し元資格情報は異なる信頼関係を表すため、相互に再利用すべきではありません。

## トラフィック境界のポリシー

ゲートウェイポリシーは、テナント、モデル、プロバイダー、MCP メソッド、ツール名、リモートエージェント、リージョン、データ分類、クォータ、委任元主体を評価できます。サーバーへの接続許可は、そのサーバーが公開するすべての能力を呼び出す許可より広いため、ツール単位の認可が重要です。

ポリシーには信頼できる入力が必要です。生成テキストは利用者の意図の証明ではなく、認証済みエージェントが任意のタスクを委任できるわけでもありません。影響の大きい操作では、副作用を所有するアプリケーションやシステムで同意・承認を得ます。ゲートウェイは承認の証跡を要求・検証できますが、承認ワークフローそのものを所有しません。

## データとコンテンツの制御

プロンプトと応答の検査は、機密データ、禁止された送信先、悪意あるツール内容、ポリシー違反を検出できます。しかし検査によってゲートウェイ自身が機密ペイロードへアクセスするため、データ最小化、暗号化、マスキング、リージョン処理、保存期間、管理者アクセス制御が必要です。

MCP のツール説明と結果、A2A のメッセージと成果物、検索したコンテンツは信頼できない入力として扱います。スキーマ検証やコンテンツ制御はリスクを減らしますが、事実性や業務上の安全性を証明しません。

## ガバナンスと監査可能性

監査記録では、呼び出し元、委任元主体、選択したルート、ポリシー版、判断、モデルまたは能力、結果を関連付けます。明確な要件がない限り、完全なプロンプト、応答、ツール結果は保存しません。拒否記録は、ポリシーによる動作とサービス障害を運用者が区別できる程度に説明可能であるべきです。

ポリシーには所有者、レビュー、テスト、段階的展開、ロールバックが必要です。ライフサイクルを管理せずに強制だけを集中化すると、設定リスクを集中させるだけです。

## まとめ

ゲートウェイのセキュリティは、ID と委任の維持、認証情報の分離、限定されたポリシーの強制、検査データの最小化に依存します。ゲートウェイは強制境界であり、利用者の同意、ドメイン認可、結果検証、責任あるポリシー所有の代替ではありません。
