デリバリーはソースコードの変更を、稼働環境における制御された結果へつなげます。DevOps は、その経路を高速で再現可能、観測可能、説明可能にするための人、プラクティス、プラットフォーム機能を結び付けます。

## 変更から本番環境まで

デリバリーシステムは、ソースコードと設定をバージョン付きアーティファクトへ変換し、評価し、環境間で昇格させ、利用者へ振る舞いをリリースします。各変換では識別子と検証記録を保持し、何が変わり、どう構築され、どの検査を通り、どこへデプロイされ、どう復旧できるかを追跡できる必要があります。

ビルドシステムはソース入力を再現可能な出力へ変換します。アーティファクト管理は、出力に安定した識別子、完全性情報、来歴、保持規則、制御された昇格を与えます。CI は変更を頻繁に統合して迅速なフィードバックを生みます。継続的デリバリーはソフトウェアをリリース可能に保ち、継続的デプロイは条件を満たした変更を本番へ自動リリースします。

## リリースとデプロイの違い

デプロイはソフトウェアの版を環境へ配置し、リリースはその振る舞いを利用者やワークロードへ公開します。両者を分離すると、フィーチャーフラグ、段階的公開、ダークローンチ、制御された実験が可能になります。

ローリング、Blue-Green、カナリアは置換と公開を異なる方法で管理します。どの方法もリスクを消しません。互換性、状態移行、トラフィック制御、オブザーバビリティ、ロールバック、複数版の運用コストに応じて選択します。

プログレッシブデリバリーは、本番環境から得られる指標を利用して公開範囲を拡大または停止します。成功基準が明示され、テレメトリが適時に得られ、シグナルが一致しない場合に対応できることが前提です。

## インフラストラクチャとプラットフォーム

Infrastructure as Code は環境の意図をバージョン管理・レビュー可能な定義として表します。GitOps は宣言状態と稼働環境を継続的に照合する調整を適用します。どちらも追跡可能性を高めますが、検証、アクセス制御、ドリフト管理、復旧手順なしに安全性を保証しません。

プラットフォームエンジニアリングは、繰り返し必要になるデリバリーと運用能力を、プロダクトチームが再構築せず利用できる支援された経路へまとめます。[内部開発者ポータル](../idp/) はそれらを見つけやすくし、プラットフォームは実際のワークフロー、環境、ポリシー、サービスを提供します。

## 運用モデルとしての DevOps

DevOps はチーム名でも自動化ツール群でもありません。共有所有、フィードバック、自動化、学習を通じて開発と運用の距離を縮める運用モデルです。プロダクトチームは本番結果とのつながりを保ち、専門家は再利用可能な機能とガードレールを構築します。

デプロイ頻度、リードタイム、変更失敗率、復旧時間は、学習に用いれば待ち時間や摩擦を示します。単独の目標にすると、定義の縮小、作業の隠蔽、安全でない行動を促すことがあります。

## よくある誤解

- **パイプラインだけがデリバリーシステムではありません。** アーティファクト、環境、権限、公開制御、テレメトリ、人の判断も含みます。
- **自動化は説明責任をなくしません。** 判断をコード、ポリシー、例外処理へ移します。
- **ロールバックは常に巻き戻しではありません。** データ移行、メッセージ、外部副作用には前進復旧が必要な場合があります。
- **標準化は正当な違いを消すべきではありません。** 共通ニーズを標準化し、明示的な例外経路を残します。

## まとめ

デリバリーと DevOps は変更を追跡可能な本番結果へ変えます。ビルド、アーティファクト、CI/CD、デプロイ戦略、インフラ定義、プラットフォーム機能は、自動化自体ではなく、安全で持続可能な流れを目的とする一つのフィードバックシステムです。
