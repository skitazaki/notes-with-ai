ハーネスエンジニアリングは、AI エージェントが作業する環境を設計します。ハーネスは指示、コンテキスト、ツール、権限、実行分離、フィードバック、状態、人の確認点をまとめ、信頼できるワークフローへ変えます。

分かりやすく言えば、モデルは意思決定エンジンであり、ハーネスはそのまわりに置かれる実行基盤です。モデルが提案する行動を、どこまで許し、どのデータを見せ、どのツールを使わせ、どの環境で動かし、どの検証を通して変更を受け入れるかを決めるのがハーネスです。

リポジトリ固有の運用指示は [AGENTS.md](/ja/docs/ai/context-engineering/agents-md/) に置き、再利用可能な手順や資源は [エージェントスキル](/ja/docs/ai/context-engineering/agent-skills/) にまとめます。[ツールと MCP](/ja/docs/ai/context-engineering/tools-and-mcp/) はツールアクセスと標準の定義場所です。これらは同じハーネスの一部であり、エージェントが何をできるか、何を知っているか、どのように作業を検証するかを定義します。

## ハーネスが担う責務

ハーネスは単一のプロンプトではありません。タスク全体を通じてエージェントの振る舞いを支配する、複数の制御層です。実務上は、次のような要素を組み合わせて設計します。

### 1. タスクの定義と制約

タスクには、意図する成果、範囲の境界、不変条件、完了の証拠を明確に定義する必要があります。モデルの性能より、タスクの定義が重要なことが多いです。曖昧な依頼は広い探索、弱い判断、見えない前提に繋がりやすく、明確なタスクは探索領域を狭め、結果を検査しやすくします。

良いタスク定義は次の問いに答えます。

- 何を解決しようとしているか
- スコープ内と外をどう切るか
- どの振る舞いの変化が期待されるか
- どの検査が完了の証拠になるか
- どの副作用に人の承認が必要か

最も強い定義は、詩的な説明ではなく、リポジトリ操作と検証基準に落とし込まれたものでしょう。

### 2. 信頼できるコンテキスト

コンテキストはまとめて投げる情報ではなく、エージェントが信頼して使える事実の集合です。良いコンテキストは小さく、最新で、修正対象のコードと整合している必要があります。リポジトリ指示、アーキテクチャ文書、Issue の説明、直近の差分、失敗ログ、テスト結果が役に立つのは、それらが実際の判断に直結するときです。

よくある失敗は、広く浅いリポジトリ情報や履歴の断片を詰め込みすぎることです。ノイズが増え、必要な制約が埋もれ、不要な情報が漏れます。ハーネスはタスクの判断に必要な最小限の権威あるコンテキストを提供し、ソースオブトルースとコメントや信頼できない入力を分けるべきです。

実務では、次のように分けて扱うと整理しやすくなります。

- 永続的なリポジトリ方針: アーキテクチャ境界、規約、コマンド、所有権ルール
- タスクコンテキスト: Issue、PR、失敗しているテスト、ユーザーの目的
- 実行時の証拠: ログ、ビルド結果、失敗トレース、環境状態
- 低信頼の材料: Web ページ、Issue コメント、生成された要約、古い誤記を含む文章

### 3. ツールの公開範囲と権限制御

ツールの公開範囲は、エージェントが実際に使える機能を定義する境界です。どの操作を提供するか、どの引数を受け取るか、各操作がどの権限を持つかを決めます。ハーネスが決めるのは、エージェントに「何が使えるか」というインターフェースの側面です。

ここでの責務と、次の実行環境の責務は違います。権限の境界は「このエージェントは何を実行できるか」を決め、実行環境は「このエージェントが実際にどこまで触れるか」を決めます。

良いハーネスは次のように分けて設計します。

- 読み取りツールと書き込みツールの分離
- ローカルのリポジトリ操作と外部のリモート操作の分離
- シェル実行とファイル編集の分離
- API アクセスと認証情報利用の分離
- 人間の承認が必要な操作と自律実行可能な操作の分離

少なくともハーネスは次の権限を個別に決めるべきです。

- リポジトリやファイルの読み取り
- ファイルの書き込みやブランチ作成
- シェルでの実行
- 外部 API やネットワーク経由のワークフロー実行
- 認証情報やシークレットの利用
- 環境変更や本番システムへの影響
- メッセージ送信や外部成果物の作成

権限は便宜ではなくリスクに基づいて付与しなければなりません。リポジトリを読むことと、本番環境を変更することは別であり、ファイルを書き換えることと、データベースを更新することも別です。各権限は明示的に管理し、レビュー可能にする必要があります。

ネットワークアクセスや認証情報利用は、ツールの公開範囲と密接に関係しますが、ここでの責務は「どの能力を公開するか」「誰が使えるか」を決めることです。実際のネットワーク出口制御やシークレットの保持方法は、次の実行環境の責務です。

### 4. 実行の分離と実行環境の境界

実行環境は、プロンプト品質と同じくらい重要です。ローカルの作業ディレクトリ、専用の worktree、一時的な CI 実行環境、リモートホストで動くエージェントは、触れるものと観測できるものが違います。

この層では、作業がどこでどのように動くか、どこまで到達できるか、認証情報がどう解決されるかを管理します。ツールの公開範囲が「使える機能の定義」であるのに対し、実行環境の境界は「その機能がどこまで安全に使えるか」を決める役割です。

良い実行分離は少なくとも次の保護を提供します。

- ファイルシステム分離: 別のチェックアウトや worktree でタスク間干渉を防ぐ
- プロセス分離: 限定されたシェルアクセスで破壊的なコマンドと広域プロセス実行を防ぐ
- ネットワーク分離: 送信の制限で悪用され得る接点とデータ漏えいを抑える
- 認証情報分離: シークレットをモデルコンテキストに置かず、承認されたスコープ付きの方法で注入する

ハーネスはセキュリティだけではなく、エージェントの振る舞いを予測可能にするための仕組みでもあります。制御された環境は、失敗の診断と再現をしやすくします。ここでの責務は、ネットワーク出口のポリシー、シークレット管理、ランタイムのサンドボックス設計です。これはツールの公開範囲とは別の責任分担です。

### 5. フィードバックと可観測性

エージェントには、解釈して次の行動へ使えるフィードバックが必要です。高速で焦点を絞った検査は局所的な編集を導き、広いテストとビルドは統合への影響を検出し、表示や振る舞いの確認は静的検査では分からない点を検証します。

ハーネスは、ループを短く、可視化しやすくする必要があります。

- エージェントは、すぐに焦点を絞った結果を受け取る
- 失敗は診断に必要な状態と一緒に伝わる
- 次の行動は、その証拠が支える範囲に限定される
- 確信が弱い結論は、黙って前に進めない

有用なフィードバックは、合否だけでなく、どのコマンドを実行し、どのファイルを確認し、どの出力が出たかまで含めます。たとえば「失敗した」という結果だけを返すのではなく、失敗箇所とログの要点まで返せば、モデルは根拠に基づいて次の修正を選べます。逆にこの根拠を返さないハーネスでは、モデルは事実ではなく推測で行動を決めやすくなり、無駄な試行や誤修正が増えます。

### 6. 状態、記憶、協調

良いハーネスは記憶を隠れた会話履歴ではなく、明示的な状態として扱います。計画、差分、ツール結果、検証結果、重要な判断は、ステップやセッションをまたいで保持すべきです。

これは複数のエージェントや人が参加するときに特に重要です。次のような問いに答えられる必要があります。

- どのファイルやブランチを誰が所有しているか
- 何がすでに検証済みか
- 現在の計画は何か
- どこが未レビューか

明示的な状態管理がないと、重複した編集、古い前提、競合する計画、曖昧な引き渡しが起こります。協調的な作業では、ハーネスは並列作業の前に、所有権と統合点を定義すべきです。

## 人間の確認点と承認設計

Human-in-the-loop は、一回の「続行しますか？」ダイアログではありません。重要な判断がある場所に、意味のあるレビューを置くことです。正しい確認点は、行動が高コストで、取り消しが困難で、運用上センシティブなときに出現します。

有効な確認点には次が含まれます。

- 意図する行動と正確な範囲
- 予想される影響と対象となるシステム
- 可能なロールバックや復旧手段
- すでに収集された判断材料
- 人間が承認するべき判断の内容

確認点は「この操作を承認しますか？」のような判断内容が分かるメッセージで、人間の役割と意思決定のトレードオフが見える形にします。これにより、価値の低い確認を増やして慣れさせることと、重要な判断の前に介入できる余地を失うことの両方を避けられます。

## 典型的なハーネスパターン

タスクの性質によって、必要なハーネスの形は変わります。同じモデルとツールスタックでも、使い方は複数のパターンに分かれます。

### 焦点を絞ったエディタ支援

このパターンは、一つのファイルや小さな範囲の修正に向きます。ハーネスは操作の負担を抑えつつ高速なフィードバックを重視し、コンテキストと権限を狭く保ちます。読み書きの権限は限定され、レビューも軽くできます。

### リポジトリ単位のタスクエージェント

複数ファイルにまたがる実装やバグ修正に向くパターンです。リポジトリを理解したコンテキスト、明示的なタスク境界、制御された worktree、検証ループを持ちます。複数ステップの実行と、手直し・再チェックを前提に設計されます。

### 委任型自動化や Issue 主導のエージェント

定常的な運用タスクや特定の Issue を対象に、継続的に作業する場合に向きます。長い間隔で再開することが多く、状態管理、権限境界、結果の要約が重要になります。再開時の一貫性を保つには、手順を [エージェントスキル](/docs/ai/context-engineering/agent-skills/) として明示しておく設計が有効です。

### マルチエージェント協調

複数のエージェントが並列に動くとき、ハーネスは共有境界と統合ルールを定義する必要があります。独立した作業ストリームは、ファイルの所有権、作業ツリーやブランチ分離、明示的なタスク分割で隔離します。並列化の利点を活かすには、ハーネスが協調の設計まで担う必要があります。

## よくある失敗モード

設計が不十分なハーネスは、次のような典型的な問題を引き起こします。

- モデルに不要な情報を多く与え、実際の制約が見えなくなる
- ツールが広すぎて、明確な制限なく書き込みやコマンド実行が可能になる
- 環境がタスク間で共有され、状態が漏れ出し、結果が一貫しなくなる
- 検証が遅く、隠れた仮説がパッチの形を決めてしまう
- 人間のレビューが危険な行動の後になり、修正が難しい
- モデルにセッションをまたいだ意図の記憶を依存させ、明示的な状態を持たない

ほとんどの失敗はモデルの失敗ではなく、ハーネスがタスクを十分に制約し、観測し、検証していないことに起因します。

## 設計原則

堅牢なハーネスは、次の原則に従います。

- タスクを実行手順と完了条件に分解してから着手する
- 目的に直接関係し、最新版で、出典が明確なコンテキストだけを渡す
- 過大な汎用権限を避け、用途を限定した安全なツールを公開する
- 読み取り、書き込み、実行、ネットワーク、認証情報を分離する
- 実行環境と状態を明示的に管理する
- 速く意味のある検証でフィードバックループを閉じる
- 本当に意思決定が必要な場所に人間のレビューを置く

## まとめ

ハーネスエンジニアリングは、一般的なモデル能力を制約された工程へ変えます。モデル単体ではなく、モデルの周囲にある指示、コンテキスト、ツール、権限、実行環境、フィードバックループ、確認点が、体系として機能します。良いハーネスは作業を検査可能で、監査可能で、回復可能にし、AI を「賢い会話ツール」ではなく「使えるエンジニアリングパートナー」へ変えます。
