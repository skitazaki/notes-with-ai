シングルサインオンとフェデレーションは、利用者が一度だけ身元を証明し、そのアイデンティティを複数のアプリケーションや信頼ドメインで使えるようにする仕組みです。各システムごとにパスワードやアカウントモデルを別個に持つ必要がなくなります。

## 概要

SSO はしばしば利用体験の改善だけと見られますが、エンタープライズアーキテクチャでは信頼とガバナンスの制御装置です。パスワードの散在を減らし、本人確認と強固な認証を中央集約し、リスクの高いアクセス判断を監査しやすくします。フェデレーションはこの特性を組織境界をまたいで拡張し、ある信頼ドメインが別の信頼ドメインからの認証主張を受け入れ、自身のポリシーで判断できるようにします。

設計上の重要な違いは、認証と認可の分離です。認証は「あなたは誰ですか？」に答えるもので、SSO とフェデレーションは主にそのアイデンティティをシステム間で確立・伝播する仕組みです。認可は「何ができますか？」に答えるもので、アクセス制御全体では別の責務です。多くの組織ではこの区別が曖昧になり、SSO を認可の問題を自動的に解決するものだと誤解してしまいます。

現代の SSO は、IdP（アイデンティティプロバイダ）、SP（依拠側、アプリケーション）、認証プロトコル、セッション管理を伴う構成が中心です。代表的なパターンには、エンタープライズのブラウザ連携に使われる SAML、モダンな Web やモバイルに適する OpenID Connect、委任認可のための OAuth 2.0 があります。どれも役割が異なり、設計の正解は「どれが最良か」ではなく、信頼境界、利用体験、ガバナンス要件に適したプロトコルを選ぶことです。

## 主要概念

### 基本的な信頼モデル

アイデンティティ基盤は、次の役割を分離して考えると整理しやすくなります。

- **主体**: 認証される利用者や実体
- **アイデンティティプロバイダ（IdP）**: 身元を確認し、主張を発行する機関
- **依拠側（SP）**: 認証主張を受け取り、アクセスを許可するアプリケーションやサービス
- **信頼ドメイン**: アイデンティティのルールとガバナンスが定義されるセキュリティ境界
- **認証主張（Assertion）**: 利用者が認証され、属性やクレームを含むステートメント
- **セッション**: 利用者がある境界内で認証済みであり続ける期間

このモデルが示すように、フェデレーションは単なる利便性ではなくガバナンスです。依拠側は利用者のパスワードや本人確認プロセスを自分で持つ必要はなく、IdP の証拠を信頼し、自身のポリシーとリスク判断を適用すればよいのです。

### SSO が存在する理由

SSO を導入する最も重要な理由は、ユーザー体験の向上だけではありません。アイデンティティの散在を減らし、どの認証方法と強度を使うべきかを統制しやすくすることです。SSO がない場合、各アプリケーションが独自にパスワードモデル、パスワードリセット、MFA、ライフサイクル管理を持つことになり、運用のばらつき、保証水準の低下、リスクの増大を招きます。

SSO は次のような統制機能を集約します。

- 一貫した本人確認と認証ポリシー
- 中央集約された MFA と追加認証
- 認証イベントの可観測性向上
- 条件付きアクセスの適用しやすさ
- アイデンティティガバナンスの責任分担の明確化

そのため、組織では SSO を利用者向けのアクセス層として使い、認可ルールはアプリケーションやポリシーエンジン、サービス層に残す設計が一般的です。アイデンティティ基盤が利用者を認証し、アプリケーションがその人に何をさせるかを判断します。

## フェデレーションプロトコルの実務

### SAML

[SAML](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf) は、ブラウザ中心の SaaS アプリケーション、既存のエンタープライズアプリ、厳密に管理された社内 ID フローがある環境で依然としてよく使われます。エンタープライズから SaaS へのサインインや、成熟したフェデレーション基盤を持つ事業者にとって重要なプロトコルです。

SAML の強みは、エンタープライズ向けの信頼関係と運用実務の成熟度です。組織が明示的な信頼関係と、広く理解されている Web SSO の考え方を重視するなら適しています。一方で、OIDC ベースのフローと比べると、モダンなモバイルや API 中心のアーキテクチャでは冗長で、開発者体験も劣りやすくなります。

### OpenID Connect（OIDC）

[OpenID Connect (OIDC)](https://openid.net/specs/openid-connect-core-1_0.html) は、モダンな Web、モバイル、API 駆動のアプリケーションに適した選択肢です。OAuth 2.0 をベースにしており、ID トークンとディスカバリー情報を通じて標準化された利用者 ID の表現を提供します。利用者体験、開発者向けツール、クラウドネイティブな統合に適しているため、現代の認証では支配的な位置を占めています。

重要なのは、[OAuth 2.0](https://www.rfc-editor.org/rfc/rfc6749) は主に認可のための枠組みであり、OIDC がその上で利用者 ID を安定して扱う層を追加している点です。セキュリティチームは OIDC を使ってアプリケーションに利用者を認証させ、認可判断そのものはアプリケーションのポリシーロジックに委ねることが多いです。IdP が最終的な認可機関になるとは限りません。

### OAuth 2.0 と委任

[OAuth 2.0](https://www.rfc-editor.org/rfc/rfc6749) は、利用者のパスワードを第三者アプリケーションに渡さずに、委任されたアクセス権を与える必要がある場合に重要です。利用者がアプリケーションに一部のリソースへのアクセスを許可したり、サービスが別のクライアントに代わってアクセスを要求したりするケースに向いています。これは、すべてのアプリケーションごとに利用者を通常の SSO フローで認証するのとは異なる話です。

この区別は運用上重要です。多くのチームが「OAuth ログイン」と言っているとき、実際には「利用者認証と委任トークン発行」を意味しているだけの場合があります。設計上は、次の責務を明確に分離するほうが安全です。

- 利用者の身元認証
- 委任された権限
- トークンの audience と scope
- アプリケーションやポリシー層での認可判断

## 設計パターン

### 中央集約したアイデンティティとローカル認可

最も一般的なエンタープライズ構成は、中央の IdP が利用者を認証してトークンを発行し、各アプリケーションが独自の認可ポリシーを持つ形です。これにより認証情報の散在は減り、アイデンティティの保証水準を揃えやすくなります。一方で、アプリケーションごとの権限モデルやロール設計は保ちやすくなります。

このパターンがうまく機能するのは、次のような場合です。

- アプリケーションごとに業務コンテキストが異なる
- アクセスポリシーがアプリケーションや部署ごとに異なる
- ローカルのリソース所有権を明確にしたい
- 認証は標準化したいが、認可は一つの万能モデルに統一したくない

### 組織をまたぐフェデレーション

フェデレーションは、パートナー、契約社員、顧客向けサービスなどの外部利用者にとっても重要です。この場合、IdP の信頼ドメインとアプリケーションの信頼ドメインは分離されています。アプリケーション側は外部の認証主張を受け取り、自身のローカルポリシーに基づいて、その主体がそのリソースとやり取りできるかを判断します。

このパターンは重複を減らしながら、セキュリティ境界も維持できます。一方でクレームの定義、属性マッピング、本人確認の保証水準、ライフサイクル監査の仕組みを明確にする必要があります。

### 条件付きアクセスと追加認証

SSO はログインの仕組みではなく、MFA、端末信頼、地理制約、リスク評価、利用者コンテキストなどの制御を適用する場所でもあります。これらの制御はサインイン時や、高リスク操作時に発生することが多く、SSO はアイデンティティ保証とアプリケーションアクセスの境界に位置します。

例を挙げると次のようなものがあります。

- 特権利用者には MFA を要求する
- 未承認の端末からのサインインを拒否する
- 機微な管理操作では追加認証を要求する
- 通常と異なるネットワークや移動パターンをリスクとして扱う

これらの制御で、各アプリケーションが同じリスクロジックを独自実装しなくても済みます。

## 運用上の現実

### セッション管理は中核である

フェデレーションで見落としがちなのが、セッションの寿命、失効、ログアウトの意味です。サインイン時には有効に見えても、セッションが長すぎる、更新トークンが大きすぎる、アプリケーション間でログアウトが伝播しないといった問題が、ガバナンス課題になります。

安全な SSO 設計では、次を明確に定義する必要があります。

- セッションの寿命とアイドルタイムアウト
- 更新トークンのルールとローテーション
- 複数の主体間でのログアウト挙動
- ログアウトとトークン失効がローカルセッションへどう伝わるか
- 高リスク利用者に対する長寿命セッションの管理方法

### 属性マッピングとアイデンティティ品質

フェデレーションの失敗の多くは、プロトコルそのものではなくデータ品質の問題です。IdP がユーザー名、メールアドレス、グループメンバーシップ、ロールなどのクレームを出しても、アプリケーション側が異なった解釈をしたり、誤った発行元のクレームを受け入れたりすると、脆弱なアクセス条件が生まれます。

良いフェデレーション設計では、次が重要です。

- 明確な属性契約
- 利用者 ID、グループ、権限属性のマッピングルール
- クレームの発行元と Issuer の妥当性検証
- 欠落や古い属性の処理ルール
- フェデレーション設定変更のレビューと管理

### 信頼関係のレビューとライフサイクルの責任

フェデレーション関係には明確な責任が必要です。アプリケーションがどのように利用者を認証しているかはわかっていても、フェデレーション契約の所有者がいないと、信頼関係は徐々に古くなっていきます。これはレガシーアプリ、SaaS、パートナー連携が同じ IdP やアイデンティティゲートウェイに依存しているときに特に起こりやすいです。

成熟した運用では、次をレビューします。

- どのアプリケーションがどの IdP に依存しているか
- どの信頼関係が現在も有効か
- 各フェデレーション統合の事業責任者は誰か
- 各アイデンティティソースにどの保証レベルがあるか
- 信頼関係の廃止時にどう退出するか

## ガバナンスとセキュリティ統制

SSO は認可システムではありません。SSO はアイデンティティ保証と信頼の仕組みです。認可は依然としてアプリケーション、プラットフォーム、ポリシー評価層の責務です。この分離は重要です。利用者が「何ができるか」は、同じ身元であってもアプリケーションごとに異なることが多いからです。

SSO の設計は、次のような制御と組み合わせるとより強くなります。

- MFA とフィッシング耐性を持つ認証
- 端末コンプライアンスや端末信頼の評価
- リスク、文脈、業務ルールに基づく条件付きアクセス
- 従業員、顧客、パートナー、管理者向け ID の分離
- 高リスク操作に対する追加認証
- フェデレーション経路のアクセスレビューと証跡

このガバナンス設計により、利用者体験と保証水準のトレードオフを明示しながら、フェデレーションの柔軟性を保持できます。

## 典型的なアンチパターン

- SSO を認可と同一視してしまう
- 各アプリケーションが同じような認証ポリシーを独自に作る
- 従業員、契約社員、パートナー、顧客で同じ IdP と信頼モデルを使い、境界管理を疎かにする
- 受け入れるクレームの範囲が広すぎて、アプリケーション側での解釈ミスを見逃す
- アプリケーション間でセッションの寿命やログアウト伝播を無視する
- プロトコル標準があると安心し、実際の信頼境界とガバナンスモデルを見落とす

## まとめ

SSO とフェデレーションは、ログインの利便性だけではなく、アイデンティティの信頼とガバナンスの仕組みとして設計すべきです。中心となる目的は、本人確認の統制、認証保証、セッション管理を中央集約しながら、それぞれのアプリケーションやサービスにおける認可境界を明確に保つことです。

最も強いエンタープライズアーキテクチャでは、SSO を利用者アイデンティティ保証の制御プレーンとして扱い、フェデレーションをドメイン間の信頼伝播メカニズムとして扱います。これによりガバナンスを一貫させ、リスク統制を強化し、アプリケーション間で認証ロジックが分断されることを防げます。
