アーキテクチャ制約は、チームが設計判断を行う前に、解の空間を境界づける条件です。システムが必ず満たすこと、してはならないこと、依存できないことを定めます。制約を明示すれば、最初から実行不可能な選択肢を擁護する時間を減らせます。

## 定義

制約とは、アーキテクチャ上の判断を制限する条件です。技術、デプロイ先、連携方式、運用モデル、期限などを選択肢から除外します。単に重要な選好ではありません。真正な制約に反する選択肢は、その制約を持つ権限者が条件を変更しない限り、採用できません。

顧客データ基盤を設計するチームを考えます。**顧客データは日本国内に保持しなければならない**は制約です。個人を特定できる顧客データを国外のリージョンへ複製する案は、その背景にある法令、契約、ポリシーを変更せずには選べません。一方、**マネージドサービスを優先する**は、実行可能な案の間での方向づけです。セルフホスティングでも、追加の運用コストを上回る根拠があれば正当化できます。

```text
制約   → 何を必ず行う／行ってはならないか
原則   → 通常はどの方向を優先するか
判断   → この状況で何を選ぶか
```

## 制約の源泉

制約はコードベースだけでなく、システムが置かれた環境から生まれます。代表的な源泉は次のとおりです。

- 法令、規制、契約、データ所在地に関する約束
- セキュリティ要件、信頼境界、リスク受容に関する判断
- 既存の基盤、インターフェース、データ形式、移行の約束
- 予算、期限、人員、運用能力
- 物理的な場所、ネットワーク遅延、ハードウェア、ベンダーの提供範囲
- 事業方針、顧客への約束、組織上の責任分担

源泉を記録すると、誰が制約を解釈、検証、変更できるかが分かります。「日本国内に保持する」は、法令、顧客契約、社内ポリシー、リスク判断のどれに基づくかを明らかにするべきです。

## ハード制約とソフト制約

ハード制約は、選択肢が必ず満たさなければならない条件です。法令、契約、セキュリティポリシー、固定されたインターフェース、交渉できない期限などが該当します。詳細な比較に進む前に確認します。

ソフト制約は、明示的な承認と結果の理解があれば緩和できる強い制限です。固定されたリリース日、優先リージョン、予算上限は、スポンサーが変更を承認できるならソフト制約になり得ます。これは重要でないという意味ではなく、所有者、エスカレーション経路、例外のコストを明らかにするということです。

重要なのは、チームがその条件に反する案を正当に選べるか、誰が例外を承認できるかです。

## 制約と原則の違い

[アーキテクチャ原則](../principles/) は、複数の判断にまたがる持続的な指針です。既定の方向と説明責任を定めますが、通常は複数の選択肢を残します。制約は、そもそも検討できる範囲を定めます。

| 概念     | 問い                             | 選択肢への効果                   | 例                                           |
| -------- | -------------------------------- | -------------------------------- | -------------------------------------------- |
| **制約** | 何を必ず行う／行ってはならないか | 適合しない選択肢を除外する       | 顧客データは日本国内に保持する               |
| **原則** | 通常はどの方向を優先するか       | 実行可能な選択肢の既定値を定める | マネージドサービスを優先する                 |
| **判断** | この状況で何を選ぶか             | 文脈に応じた選択肢へコミットする | 日本リージョンのマネージドデータベースを使う |

選好を制約と呼べば、通常のトレードオフまで不可能に見えてしまいます。真正な境界を原則と呼べば、適合性を任意のものとして扱うことになります。両者は関連しますが、別々に記述するべきです。

## 意思決定における制約

[意思決定フレームワーク](../decision-frameworks/) では、代替案を順位づける前に制約を明らかにします。判断の対象を定め、制約、その源泉、所有者、根拠を記録します。ハード制約に適合しない案を除外してから、残る案を原則、ピラー、コスト、リスク、可逆性、根拠で比較します。

顧客データ基盤では、まず「日本国内に保持する」が、保存、処理、バックアップ、サポートアクセス、テレメトリー、災害復旧のどこまでを含むかを確認します。その範囲を満たせない案を除外します。残る案では、マネージドサービスを優先する原則が、日本リージョンのマネージドデータベースを後押しします。該当するサービスがないなら、セルフホストを選び、データ所在地の制約を例外の理由として記録できます。

ハード制約に反するマネージドサービスは「より良い」案ではなく、実行不可能な案です。一方、承認されたセルフホスト案は、制約が可能な範囲を変えたとき、必ずしも原則の失敗ではありません。

## 制約の検証と見直し

重要な制約ごとに、条件文、源泉、適用範囲、所有者、検証方法、見直し条件を記録します。曖昧な表現は、法務、セキュリティ、運用、プロダクト、顧客との約束を担う人と確認します。

契約の終了、規制解釈の明確化、基盤の機能追加、移行の完了、期限や予算の再交渉など、源泉が変わったときに見直します。制約は廃止または縮小できても、黙って消すべきではありません。

## よくある誤り

**前提を制約として扱うこと。** コスト、遅延、製品機能について未検証の考えは、選択肢を除外する境界ではなく、検証すべき根拠です。

**源泉や所有者を記録しないこと。** 曖昧さを解消できず、誰が例外を承認できるかも分かりません。

**設計を選んでから制約を見つけること。** 手戻りを生み、適合しない案を正当化したくなる原因になります。

**選好でトレードオフを隠すこと。** 「常にマネージドサービスを使う」は、責任を持つ権限者が必須規則と定めない限り、原則です。

**一時的な制限を見直さないこと。** 移行上の制限、期限、ベンダーの機能は変わります。組織の伝承として残すと、将来の選択肢を不必要に狭めます。

## 要約

アーキテクチャ制約は、判断の前に解の空間を境界づけます。原則は実行可能な選択肢の中で優先する方向を示し、意思決定フレームワークは文脈に応じた選択と結果を明示します。役割を分けることで、アーキテクチャの判断はより速く、明確になり、見直しやすくなります。
